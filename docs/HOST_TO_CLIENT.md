# HOST_TO_CLIENT.md — 盘内数据如何进面板（host → client 数据通道契约）

> 状态：**勘探完成（2026-10-08）**，结论已源码级闭合，可作为阶段 5-B 及后续一切
> 「浏览器 UI 显示 Nomad 盘内真实数据」工作的**唯一地基**。
>
> 一句话结论：**数据从 Host（Node 侧）进 Browser（client 侧），有且只有一条正规路 ——
> Typert RPC（`@deepseek-ai/dsh-typert-protocol` 的 `TypertRemoteService` + `@Remote` 装饰器）。**
> 它需要 TypeScript + 构建期生成，**不是零构建手写 UMD 能仿的**。这一点直接决定了
> `nomad-panel` 目前「零构建手写」的形态无法承载真实数据，必须另立通道或引入构建。

---

## 1. 问题的由来

`packages/nomad-panel/`（阶段 5-A 产物）是一个**零构建手写**的客户端插件：
`window.__ModuleLoader__.load({ id, factory })`，`factory(require)` 里手写 `exports.apply/inject`。
它在侧栏长出了 Nomad 入口，主区渲染了骨架面板（品牌头 / About / 状态区 / 三个占位卡片 / 回程）。

阶段 5-B 要给面板填真实内容（DSH 版本、Session 数、盘内占用、宿主隔离状态）。
这些数据的**来源在 Host 侧**（盘内文件、`data/run/`、`launcher/lib/` 的只读逻辑），
**消费在 Browser 侧**（面板 React 组件）。中间的通道是什么？这就是本文件要回答的问题。

---

## 2. 勘探结论（先给结论，证据在后）

### 2.1 正规通道只有一条：Typert RPC

Host 往 Browser 传数据的**唯一受支持机制**是 `@deepseek-ai/dsh-typert-protocol`：

| 侧 | 写法 | 关键文件（证据） |
|---|---|---|
| **Host 半** | `class X extends TypertRemoteService`，方法加 `@Remote('verb')` 装饰器；`super(ctx, 'serviceKey', { namespace })` | `packages/typert/protocol/src/index.ts:166-180` |
| **Client 半** | `class X extends Service`，`super(ctx, 'serviceKey')` 注册到 Cordis；组件通过 `ctx.get('serviceKey')` 拿到，调用方法即走 RPC | `packages/api/workspace-controller/src/client/service.ts:118-187` |

这条路的**教科书范例**是 `workspace-controller`：
- Host：`WorkspaceController extends TypertRemoteService`，`@Remote('create'/'rename'/'delete'/'follow'...)`，其中
  `@Remote({ mode: 'stream' }) follow(signal)` 返回 `AsyncIterable<WorkspaceFollowFrame>` —— **这是
  「Host 往 Browser 推状态」的官方范式**（baseline + 增量流）。
- Client：`WorkspaceController extends Service`（`super(ctx, 'workspaces')`），`IWorkspaces` 接口，
  组件消费 `ctx.get('workspaces')`。
- 两端靠 `RemoteFailure`（`remote-error.ts`）结构化报错；`bindTypertRemote`（`index.ts:152-163`）
  把 Cordis service key 绑到 wire namespace。

### 2.2 为什么我们的「零构建手写」走不通这条路的三个硬事实

1. **Typert RPC 是 TypeScript + 装饰器 + 构建期的产物**：
   `@Remote` 是标准 `ClassMethodDecorator`（`index.ts:198-211`），依赖 TS 装饰器编译；
   schema 用 `@deepseek-ai/schemastery` 的 `z.object`；类型增广靠 `declare module '@deepseek-ai/cordis'`
   （`workspace-controller/src/index.ts:43-48`）。这些都要 `tsdown` 构建，**无法用 `lib/client.js`
   手写 UMD 表达**。

2. **Host 侧 service 的注册靠 `ctx.plugin(...)` / `static inject`**（`workspace-controller/src/index.ts:51-52`，
   `static inject = ['typert', 'workspaceRegistry']`）—— 这是 Cordis 宿主插件的构造，同样要求
   host 半是一个**正经的 TS 插件包**，不是空 `apply()` 的手写壳。

3. **`dsh.client.inject` 是「信息性」边，不提供等待**（`packages/client/ui-workspace/src/client/index.ts:91-96`）：
   *"dsh.client.inject edges are informational (loading/prefetch metadata, never apply sequencing) and
   neither owner provides a waitable service."* —— 意味着即使 client 半声明了依赖，也不能假设
   host service 已经就绪，时序要靠 `slots.inject()` 而非 service 等待。

### 2.3 三条不可违反的纪律（`packages/client/AGENTS.md`）

勘探中读到、必须在任何实现里遵守的三条红线：

1. **「Live data has exactly three channels」**（AGENTS.md 第 5 条）：父知道 → owner props；
   仅组件知道 → local state；跨条目共享/跨 remount 存活 → **register 时声明的 store**。
   **「Business data lives in the object layer, never a store」** —— 会话、连接等业务数据不进 store，
   只能在 object layer（`client/connection`、`api/*-controller/client` 这类）。

2. **「A feature plugin MUST NOT runtime-import or re-export another feature plugin's values」**
   （AGENTS.md:37）：插件间数据**只能**通过「injected Cordis services」或「slots」传递，
   禁止 `dsh.client.external` 去捞别的插件的数据。**共享运行时值只该放在职责收窄的静态 owner**
   （`client/store` / `ui-primitives` / 浏览器安全 util），或 transport / 生成式 API assembly。

3. **「ctx 只在 apply 世界」**（AGENTS.md「ctx discipline」）：组件永远不碰 `ctx`，
   数据与回调全部通过「owner props / store / inject face」线程化传入。

## 3. 完整的数据通道地图（谁 provide、谁 consume）

勘探锁定的正规成对实现都落在 `packages/api/*-controller/`：

| Host 包（provide service） | Client 消费（`ctx.get` 的 key） | 通道 |
|---|---|---|
| `api/workspace-controller` | `workspaces` | Typert RPC（`TypertRemoteService`） |
| `api/session-controller` | `sessions` | Typert RPC |
| `api/account-controller` | （account 相关） | Typert RPC |
| `api/settings-controller` | （settings） | Typert RPC |
| `api/terminal-controller` | （terminal） | Typert RPC |
| `api/job-controller` | （job） | Typert RPC |

**关键事实**：UI 插件（`ui-workspace` 等）的 host 半是**空 `apply()`**（
`packages/client/ui-workspace/src/index.ts` 全文只有注释 + `export function apply(): void {}`）。
它们**从不自己 provide service** —— 它们消费的 `workspaces/sessions/remote` 全由
`packages/api/*-controller` 这些**专门的 transport/API 包**提供。这是刻意的分层
（「transport and generated API assemblies keep their explicit infrastructure edges」）。

## 4. 给 Nomad 的三条可选路径（已勘探，待维护者拍板）

> **2026-10-08 第二轮勘探修正（重要）**：路径 A（Typert RPC）的成本被上一轮低估了。
> 实测构建产物 `typert.host.js` 首行明示：`/* Generated by @deepseek-ai/dsh-typert-generator
> from FaceModel — do not edit. */`。即 `@Remote` 装饰器**不是简单编译**，而是由上游专属
> **代码生成器**（`packages/typert/generator`）从 TS 类型签名生成出 35KB 的 zod schema +
> `TYPERT_REMOTE` 描述符表（每个方法一个 descriptor：service/namespace/method/参数 codec/结果 codec）。
> 该生成器**不随运行时发布**（运行时只有 `dsh-typert-loader/protocol/registry`，无 generator），
> 且带严格 analyzer 校验（`bindTypertRemote() requires this, service key…`）。⇒
> **走正规 Typert RPC ≈ 复刻上游代码生成流水线**，不是「装个 tsdown」能了事。
> 这显著抬高了路径 A 的成本，需重新权衡（见 §6 更新）。

按「忠实于上游契约程度」从高到低：

### 路径 A —— 正规 Typert RPC（最忠实，工程量最大）
新立一个 `packages/api/nomad-status-controller`（或并入现有结构），
Host 半 `class NomadStatusController extends TypertRemoteService` 提供 `getStatus()` / `follow()`，
Client 半 `class ... extends Service` 消费。**代价**：必须引入 TypeScript + tsdown 构建链，
放弃 `nomad-panel` 当前的「零构建手写」形态。**这是唯一能拿到「官方流式推送 + 重连安全」的路。**

### 路径 B —— 轻量独立 HTTP 端点（最快，但有架构代价）
Launcher 额外起一个只回 `127.0.0.1` 的只读 `/status` 端点，面板 `fetch` 它。
**代价**：等于多了一条旁路服务，不在 DSH 的 Typert 体系内，需要 ADR 记录「为什么不用 RPC」，
且要自己处理认证（token）、生命周期、重连。**违背「不拆发动机」的纯粹性，但没拆发动机 ——
只是新增了一条不经过 DSH 的旁路。**

### 路径 C —— 复用现成 service，不自建（可能最省）
看 DSH 是否**已有**能暴露「运行时/会话数/版本」的现成 service（如 `sessions` 已能拿到会话数），
面板直接消费它，不新建任何 controller。**代价**：只能显示 DSH 已暴露的数据，
Nomad 专属的「盘内占用 / 宿主隔离状态」这类**不在 DSH 认知里**的数据拿不到。

> 三选一前，需先回答一个产品问题：**面板要显示的「盘内占用 / 宿主隔离」这类 Nomad 专属数据，
> 是不是必须实时、必须进浏览器？** 如果是「启动时看一眼就够」，路径 C + 静态注入
> （build 期把 `VERSION` 等塞进 `process.env.DSH_CLIENT_*`，见 `packages/client/AGENTS.md`
> 「Build-time browser environment」）可能就够，根本不用碰 RPC。

## 6. 下一步建议

> **2026-10-08 落地（路径 B 已实现）**：维护者逐项拍板「实时 → 低频轮询」「身份+运行态 / 健康度
> 两类内容」「新建轻量只读端点」「遵循 DSH 生命周期」后，路径 B 已落地为
> `launcher/lib/status-server.js` + `packages/nomad-panel/lib/client.js` 轮询。详见
> `docs/DECISIONS.md` **ADR-0030**。要点：
>   - 端点**固定端口**（`config.status.port`，缺省 3090），因为面板是零构建手写产物、读不到运行时
>     随机端口（`DSH_CLIENT_*` 是构建期内联），固定端口是唯一零魔法的桥接；
>   - 端点只读、只绑 127.0.0.1、白名单过滤（不泄露 launch token）；
>   - 「实时」实为「低频轮询」（缺省 5s），不承诺毫秒级推送。
>
> 若未来需要**毫秒级流式**（如把聊天事件流推进面板），再重新评估路径 A（Typert RPC）。

1. **产品问题已定：实时**（维护者 2026-10-08 拍板）。
2. **若仍走 A（Typert RPC）**：需先回答「是否要复刻/引入上游 `dsh-typert-generator` 代码生成流水线」。
   这是一个**新的架构级决策**（等于 Nomad 首次引入 TS 构建 + 代码生成），必须先立 ADR 评估，
   而非当作「填内容」的顺手活。最小 PoC 也应先证「generator 能否在 Nomad 侧跑通」这一最不确定的点。
3. **重新审视 B（独立 HTTP /status 端点）**：在「实时」需求下，B 的劣势（要自己造流式/重连/认证）
   被 A 的「复刻生成器」劣势**部分对冲**。若实时数据是「低频状态」（几秒一次心跳、面板轮询就够），
   B 的复杂度远低于 A，且完全在 Nomad 自己的 `launcher/` 体系内（不碰 DSH 生成器）。
   值得把 B 从「次选」升为「并驾齐驱」重新评估。
4. **无论哪条**：先补 ADR 到 `docs/DECISIONS.md`，记录「为什么选这条、放弃那两条」，尤其记录
   「A 需要复刻上游代码生成器」这一关键事实，避免后人误判成本。
